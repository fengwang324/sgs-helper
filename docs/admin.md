# 本地资料管理网页（`sgs_helper.admin`）

> 目标：**用浏览器维护资料，不必频繁手改 YAML**，同时保持
> `YAML 是唯一权威数据源，SQLite 只是生成物` 这条铁律不被破坏。
>
> 当前阶段只做“本地管理工具”，不是正式微信小程序，不引入 React/Vue。

技术栈：FastAPI + Jinja2 + 手写 HTML/CSS + 原生 JavaScript（约 600 行）。
数据层、校验层、构建层全部复用现有 `sgs_helper` 代码，**没有另起一套规则**。

---

## 1. 启动

```bash
# 在容器里（已挂载 /data）
cd /data/wf/1002/sgs-helper

pip install -e ".[admin]"        # 一次性：fastapi / uvicorn / jinja2 / python-multipart

uvicorn sgs_helper.admin.app:app --host 127.0.0.1 --port 8000
# 或者
python scripts/admin.py --port 8000          # 等价，带更友好的启动提示
python scripts/admin.py --port 8000 --reload # 开发用
```

浏览器访问 <http://127.0.0.1:8000>。可用环境变量：`SGS_DATA_DIR`（默认 `./data`）、
`SGS_DB`（默认 `./build/sgs.db`）。

`--host 0.0.0.0` 可以把页面暴露到局域网；本工具没有登录与权限体系，
只在可信网络里这么用（表单带 CSRF token，但这不是认证）。

## 2. 页面入口

| 路由 | 作用 |
| --- | --- |
| `GET /` | 首页：统一搜索框、各类型条数、核验状态分布、SQLite 状态、当前校验错误与警告 |
| `GET /search?q=&kind=&status=&mode=` | 跨 9 类实体检索，显示类型 / 名称 / 模式 / 来源 / 核验状态 / YAML 位置 |
| `GET /list/{kind}?q=&mode=&status=&product=&package=&page=` | 分类列表 + 筛选 + 分页 |
| `GET /view/{kind}/{id}` | 详情页（技能 / 卡牌 / 武将有专门的分层展示） |
| **`GET|POST /new/product`、`/edit/product/{id}`** | **产品专用录入页**（见第 3 节） |
| **`GET|POST /new/general`、`/edit/general/{id}`** | **武将专用录入页**（见第 3、4、5 节） |
| `GET|POST /new/{kind}`、`/edit/{kind}/{id}` | generic 表单，服务其余低频实体（技能本体、技能版本、卡牌、实体卡、FAQ、关键词、时点） |
| `GET|POST /delete/{kind}/{id}` | 删除确认 + 引用检查 |
| `GET /review[?status=]` | 待核验清单：`unverified` / `community` / `conflict` |
| `POST /rebuild` | 手动按当前 YAML 全量重建 SQLite |
| `GET /raw/{kind}/{id}` | 直接查看该记录所在 YAML 文件原文 |
| `GET /healthz` | JSON 健康检查 |
| `GET /help` | 站内使用说明 |

录入辅助 JSON API（给页面里的搜索式组合框用，也可以直接用脚本调）：

| 路由 | 作用 |
| --- | --- |
| `GET /api/skills?q=&limit=` | 技能搜索（名称 / 别名 / id），返回 `version_count` |
| `GET /api/skills/{id}/versions?mode=&product_id=` | 某技能的可选版本，按「产品匹配 > 模式匹配 > common > 其它」排序；每项带版本标签、模式、产品、生效时间、文本摘要/全文 |
| `GET /api/products?q=` | 产品搜索（名称 / ID / 年份） |
| `GET /api/suggest?field=faction|general_set&q=` | 势力 / 武将牌系列的已有值（带使用次数） |
| `GET /api/generals?name=` | 同名武将提醒（模式 / 产品 / 系列 / 编号） |
| `GET /api/version-exists?skill_id=&mode=&product_id=&text=` | 是否已有内容完全相同的技能版本 |

## 3. 产品 / 武将专用录入页

### 为什么不再用 schema 自动表单

日常录入的真实顺序是「拿着实体卡从上往下抄」，不是「按数据库字段顺序填」。
所以产品与武将改成**专用页面**：字段顺序、联动、内联新建技能/版本都是为录卡服务的。
其余低频实体（技能本体、技能版本、卡牌、实体卡、FAQ、关键词、时点）继续用 generic 表单，
两者的解析代码也分开：generic 在 `forms.py`，专用在 `editors.py`。

### 产品录入页

日常只需要 5 个字段：

| 字段 | 说明 |
| --- | --- |
| 名称 * | 这一盒 / 这一版 / 这次线下发行的产品名称 |
| 发行年份 | 可空 |
| 模式 | 固定下拉（国战 / 身份 / OL / 手杀 / 其他 / 通用），可空 |
| 武将牌 | 该产品包含的**武将牌系列 / 武将牌组名称**，标签输入，可搜索已有值、也可直接新增，支持多个 |
| 游戏牌 | 该产品包含的**游戏牌牌堆 / 牌堆系列名称**，同上 |

数据模型上这两者已经**彻底分开**：`Product.general_sets` 与 `Product.card_sets`
（旧字段 `included_sets` 把“武将牌系列”和“游戏牌牌堆”混在一起，已删除）。
填入的标签会去重并保序；`general_sets` 会作为武将录入页的候选值。

出版方、版次、系列、发行日期、来源、核验状态、备注都收进折叠的「高级信息」，
编辑已有产品时它们照常提交、不会因为主流程没展示就被清空。

### 武将录入页

首屏基本就是照着一张武将牌从上往下录：

```text
新增武将
编号 [ WEI001 ]   称号 [ 独眼的罗刹 ]   名字 * [ 张辽 ]
模式 [ 国战 ▼ ]  势力 [ 魏 ]  勾玉 [ 2.5 ▼ ]  性别 [ 男 ▼ ]
武将牌系列 [ 九变篇 ]   产品 [ 群狼环鼎 ▼ ]

技能
┌─────────────────────────────────────────┐
│ 技能 [ 突袭 ✕ ]            ↑ ↓  删除此技能 │
│ 版本 [ 初版 · 国战 · 群狼环鼎 · … ▼ ]      │
│      （选中版本后显示：模式 · 产品 · 生效时间 + 文本摘要）
│ + 为这个技能新增版本                        │
└─────────────────────────────────────────┘
+ 添加技能

[保存] [保存并新增下一位武将]  ☑ 下一位继承产品信息
```

**只有名字是必填的**。模式、势力、勾玉、性别、武将牌系列、产品、技能都可以先留空，
先把手头有的信息录进来，以后再补（详情页与待核验页会一直提醒缺什么）。

各字段的行为：

- **编号**：实体卡上的编号（`general_number`）。**不是**内部 ID，
  允许大小写字母、数字、`-`、`_`（例如 `WEI001`、`shu-01`）。
- **称号**：`title`，卡面上的称号。
- **名字**：唯一必填。输入时会调用 `/api/generals?name=` 提醒**同名武将**
  （列出模式 / 产品 / 系列 / 编号），但**不阻止**保存 —— 同名在不同产品/版本下是合法的。
- **模式**：固定下拉，可空。选了产品且产品只有一个模式时会自动带入，用户可以改。
- **势力**：可搜索已有值，也可以直接输入新值（不做固定枚举）。
- **勾玉**：底层是 `hp`（体力），下拉 1 / 1.5 / 2 / 2.5 / 3 / 4 / 5，可空。
- **性别**：男 / 女 / 未知。
- **武将牌系列**：`general_set`，可搜索已有值、也可直接输入新值；
  选择产品后会优先给该产品 `general_sets` 里的值，但仍然允许输入别的值。
- **产品**：搜索式下拉，支持按 名称 / ID / 年份 搜索。
  选中后只会给**当前为空**的字段带入模式与武将牌系列，不覆盖你已经填的内容。

### 内部 ID 与“编号”是两件事

- 页面上的「编号」是实体卡编号（`general_number`，自由字符串）。
- 真正的内部 `id`（YAML 文件名 / URL / 外键）放在「高级信息」里，**默认留空**：
  后端按名字生成合法且唯一的 ID（ASCII 名字直接转写，例如 `Zhang Liao` → `general_zhang_liao`；
  中文名退化成稳定短哈希，例如 `general_n93d5cfd3`），冲突时追加 `_2` / `_3`。
- 已存在的记录**绝不会**被重新生成 ID；改 ID 会同时移动 YAML 文件，被引用时会被校验拦下。

## 4. 技能：搜索、内联新建、内联新增版本

一行技能 = 一个「搜索式组合框 + 版本选择 + （必要时）新建区域」。

1. **绑定已有技能**：在技能框里输入名称 / 别名 / id，用 ↑ ↓ 选择、Enter 确认（Esc 关闭）。
   候选项会显示「已有 N 个版本 · skill_xxx」。搜索优先展示已有技能，减少重复创建。
2. **新建技能**：没有匹配时下拉里会出现 `+ 新建技能「xxx」`，点它就会展开
   新技能区域（**技能描述 / 技能版本 / 内部 ID**），不需要离开武将页面。
   - 只填技能名称、不填描述 → 只创建 `SkillDefinition`；
   - 填了描述 → 同时创建 `SkillVersion`（自动继承当前武将的 mode 与 product）；
   - 新技能与已有技能**同名**时会提示「仍然新建一个独立技能，请确认」。
3. **指定版本**：选中已有技能后，版本下拉里按「产品匹配 > 模式匹配 > common > 其它」排序。
   选项文本形如 `国战版 · 国战 · 群狼环鼎 · 锁定技，当……`，选中后下面还会显示
   「模式 · 产品 · 生效时间」与文本摘要，方便判断是哪一版。
   如果筛完只剩一个明显匹配的版本，会自动选中。留空表示「不指定」，
   详情页按 `mode + effective_from/effective_to` 自动推导。
4. **为已有技能新增版本**：展开「+ 为这个技能新增版本」，填版本名称（可空）与技能描述即可；
   「基于当前版本新增」会把当前版本的文本复制过来，并把当前版本填进 `previous_version_id`。
   保存时是**新增**一条 SkillVersion，旧版本文件字节不变。
5. **删除技能**：只删掉这个武将与技能的引用关系，**不会**删除全局 Skill。
6. 技能顺序就是卡面上的顺序，用 ↑ ↓ 调整。

如果新版本的 技能 + 模式 + 产品 + 文本 与已有版本完全一致，
保存时会**直接复用**那条版本并在页面提示，不会产生重复版本。

## 5. 一次提交 = 一个事务

武将录入页一次提交最多同时产生：

```text
1 个 General + 0..N 个新 Skill + 0..N 个新 SkillVersion + 多条 General→Skill/Version 关系
```

`AdminStore.save_batch()` 把它当成**一个事务**：

```text
解析 General + 新 Skill + 新 SkillVersion
        ↓
把所有候选变化同时合入内存中的 DataBundle
        ↓
完整 validate_entities()（模型 + 交叉引用 + 一致性 + 重复 id）
        ├─ 任何一条不合法 → 一个文件都不写，页面给出 文件/字段/原因
        ↓
备份所有将要修改的 YAML
        ↓
一次性全部写入（临时文件 + fsync + os.replace）
        ↓
只 rebuild 一次 SQLite（先写临时库，成功后原子替换）
        ↓
成功
```

任何一步失败：所有相关 YAML 全部回滚（被外部改动过的文件跳过回滚）、
原数据库保持不变、页面保留你填过的内容，并指出是哪个技能/哪个字段出错。

## 6. 写入流程与安全（为什么不会把资料写坏）

```text
浏览器表单
   │  editors.py / forms.py 解析成候选实体
   ▼
AdminStore.save_batch()
   │ ① 并发检查（_base_sha 记录内容哈希）
   │ ② 内存预校验 validate_entities()，不通过则一个字都不写盘
   │ ③ 备份 + 原子写入所有 YAML
   │ ④ build_database()：临时库 → os.replace，只 rebuild 一次
   └─ 失败：回滚（不覆盖外部修改）+ 旧数据库原样保留
   ▼
303 重定向到详情页
```

关键点：

1. **读也走 YAML**。列表、详情、搜索都直接读权威源；搜索复用
   `db._search_row` + `repo._score`。SQLite 过期时页面顶部会提示重建。
2. **SQLite 只由 `build_database()` 全量重建**，网页没有任何一处直接
   `INSERT/UPDATE/DELETE` 数据库。
3. **先校验后落盘**，磁盘上不会出现半合法的 YAML；写盘后 `build_database` 还会从磁盘再校验一次。
4. **并发保护**：编辑页带该记录的**内容哈希**（`_base_sha`），提交时对不上就拒绝写入并提示刷新。
   HTTP 层强制要求这个字段存在。注意哈希是**记录级**的：别人只改了同文件里的注释、
   没改这条记录的内容，不会触发冲突。
5. **原子写**：`临时文件 → fsync → os.replace`；重建数据库同样先写临时库再原子替换。
   回滚前会比对“文件内容是否仍等于我们刚写进去的内容”，被外部改过就跳过回滚并说明。
6. **CSRF token**：所有写操作都要带页面里的随机 token。

写 YAML 的可读性：字段顺序按模型顺序；规则文本类字段用块状标量（不折行）；
文件顶部注释块保留；原来是单条 / 列表 / `items:` 包装就还是哪种结构。

## 7. 键盘、草稿与连续录入

- **Tab / Shift+Tab**：按录入顺序移动。
- **搜索框**：↑ ↓ 移动候选，Enter 确认，Esc 关闭。
- **Ctrl/⌘ + S**：保存。
- **Ctrl/⌘ + Enter**：快速添加下一个技能行。
- **+ 添加技能**：点一下加一行，光标停在技能搜索框，可以一路键盘录下去。
- **保存并新增下一位武将**：保存成功后直接打开新的武将录入页，
  默认继承上一条的 产品 / 模式 / 武将牌系列（「下一位继承产品信息」可以关掉）。
  名字、编号、称号、势力、勾玉、技能都不继承。
- **以此武将为模板新增**：详情页上的按钮，带入 产品 / 模式 / 武将牌系列，
  并通过勾选框决定是否复制 势力 / 勾玉 / 性别 / 称号；名字、编号、内部 ID、技能一律不复制。
- **草稿**：录入页会把未提交的内容存进浏览器 `sessionStorage`；刷新或误关后重新进入，
  页面会提示「发现未保存的草稿」并提供 恢复 / 丢弃。草稿只在本地，不会覆盖服务器已有数据。
- **离开提醒**：有未保存改动时关闭页面会提示（沿用原有 dirty form 保护）。

## 8. 删除规则

删除前用 `REFERENCE_FIELDS`（与校验器同一张声明表）反查引用，支持嵌套路径：

- 有引用 → **拒绝删除**，页面列出引用方（类型 / 名称 / id / **字段路径**，
  例如 `skills[0].version_id`）；
- 无引用 → 先做一次「删掉这条之后数据集是否仍然合法」的预校验，通过才删；
- 删技能版本时，如果它被某个武将显式绑定、或有后继版本（`previous_version_id`），会被拒绝；
  只是历史版本时可以删，删除确认页会说明它是不是「当前有效版本」。

另有一条测试保证：任何新增的 `*_id` / `*_ids` 字段（包括嵌在关系结构里的
`skills[].skill_id` / `skills[].version_id`）都必须在 `REFERENCE_FIELDS` 里声明，
否则测试直接失败 —— 防止以后加了引用字段而删除保护静默失效。

## 9. 武将 → 技能 → 版本的数据模型

武将不再用平行的 `skill_ids: [...]`，而是显式的关系统构：

```yaml
# data/generals/xxx.yaml
skills:
  - skill_id: skill_mingshi
    version_id: skill_mingshi_guozhan_v1   # 这张卡印的就是这一版
  - skill_id: skill_lirang
    version_id: null                       # 暂不指定 -> 详情页自动推导
```

- `skill_id` 必填，指向 `SkillDefinition`；
- `version_id` 可空；不为空时**必须属于同一个 skill_id**（校验器强制）；
- 不用两个平行数组，避免顺序错位；
- 详情页：显式绑定优先显示指定版本（标记「按卡面指定」），否则按
  `mode + effective_from/effective_to` 推导当前有效版本（标记「自动推导」）；
- SQLite 侧落到 `general_skills(general_id, skill_id, version_id, position)`，
  `position` 就是卡面上的技能顺序。

## 10. 待核验流程

`/review` 按 `verification_status` 汇总 `unverified` / `community` / `conflict`。
逐条打开 → 对着实体卡核验 → 改核验状态、把 `source.type` 换成 `physical_card`
并填 `source.title` / `source.reference` → 保存。
source 与核验状态都在录入页的「高级信息」里，日常录卡可以先不管（默认 `unverified`，
会进待核验页面）。

## 11. 已知限制（有意为之）

1. **写 YAML 会规范化格式**：记录内部的行内注释、锚点/别名、原有引号风格不会保留
   （保留的是：字段值、字段顺序、文件顶部注释块、文件结构）。
2. **一个文件多条记录**（例如手工把多条 keyword 放进同一个列表文件）编辑其中一条会整文件重写；
   其他记录的**内容**不变，但格式也会被规范化一次。当前 `data/` 里一条记录一个文件。
3. **中文名生成的内部 ID 是短哈希**（`general_n93d5cfd3`）。想要可读的 ID，
   在「高级信息 → 内部 ID」或技能行的「内部 ID」里自己填。
4. **版本选择是原生 `<select>`**：选项文本里带了版本标签 / 模式 / 产品 / 文本摘要，
   选中后下面还有一段预览。没有做成两行富文本下拉（保持键盘与无 JS 可用）。
5. **并发保护是记录级哈希**：只改注释不会触发冲突（这是刻意的，避免同文件多记录互相干扰）。
6. **旧字段不再兼容**：`included_sets` / `skill_ids` / `package`(武将) 已从模型里删除，
   旧 YAML 会直接报“未知字段”，需要按第 9 节的新结构迁移（示例数据已经迁移过）。
7. **列表字段是“一行一项”文本**：空行忽略、首尾空格去除。
8. 本地工具：没有登录/权限/审计；`--host 0.0.0.0` 时请只放在可信网络。
9. 不做并发写入合并：同一记录被两处同时改，后提交方被拒绝并要求刷新。
10. 不是小程序后端：未来接小程序请从 `sgs_helper/repo.py`（只读 SQLite）那层开始。
